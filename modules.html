Start Here

Your first self-directed modules. Work through them at your own pace — each one ends with something you have to show, not just read.

These modules sit on top of the Learning Progression (the map of all seven levels), and together they cover the whole arc — from the on-ramp to a shipped capstone. Links point to official docs; commands, model names, and versions change, so when in doubt, trust the official page over any screenshot or older tutorial.

Read this first: you are not here to "use AI." You're here to do the thing organizations pay for and rarely find — take an open model, get it running on real hardware, serve it, connect machines together, and build on top. Nobody expects you to know this yet. Follow the modules, get stuck, ask, and keep a log of what you tried. The log is half the skill.

How to work

Keep a running notebook (paper or a doc). For every step, write what you ran, what happened, and what you changed. When something breaks — and it will — that log is what turns a frustrating hour into a skill you own. "Read the error message out loud" solves more problems than anything else in this lab.

Module 0

On-ramp — learn the language

Goal: Be able to explain, in plain English, what an open-weight LLM is, and be comfortable enough with Python and the terminal to read and edit a short script.

What you'll do

  1. Create a free account at huggingface.co. This is where the open models live.
  2. Work through the opening chapters of the Hugging Face LLM Course — enough to understand what a "model," a "token," and "the Transformers library" mean.
  3. Get comfortable in a terminal (navigate folders, run a Python file) and learn Python basics if you haven't. Aim toward the PCEP level — it's the cheapest real certification you can earn and a clean first goal.
  4. Open five real model cards on the Hub (for example, search Qwen3-8B, gemma, gpt-oss-20b). For each, find its size, its license, and whether it's a "base" or "instruct" model.

What these words mean

  • Open-weight model: the actual trained model is downloadable and you can run it yourself — no company's server required.
  • Base vs instruct: a "base" model just continues text; an "instruct" (or "-it") model has been trained to follow instructions and chat. You almost always want instruct.
  • License: the rules for using a model. Some (Apache 2.0) are wide open. Some (Meta's Llama) make you accept terms first — that's called "gated."
Prove it In your notebook, write a short paragraph a friend with zero background could understand: what an open-weight LLM is, and the difference between a base and an instruct model. Then list your five model cards with each one's size and license.
Module 1

Run — your first local model

Goal: Get an open model running on a lab machine, chat with it, and then talk to it from your own Python script through its API.

This is the module where it clicks. By the end, a real AI model will be answering you — running entirely on the computer in front of you, with no internet connection required once it's downloaded.

Part A — Get it talking

  1. Install Ollama on your lab machine (follow the official install page for your operating system).
  2. Pull an open model with ollama pull qwen3:8b (or whichever model your teacher points you to — check the exact name on the Ollama model list, since names change).
  3. Start chatting with ollama run qwen3:8b. Ask it something. You're now running a local LLM.
  4. Watch your GPU while it runs. Notice how much VRAM the model uses — that number is why you can't just run any model on any machine.
Pick an ungated model first

Start with an Apache-2.0 model like Qwen or Gemma or gpt-oss — they download with no license step. Save the Meta Llama models for later, once you understand why some models make you accept terms before you can use them.

Part B — Talk to it from code

Chatting in the terminal is fine, but the real skill is calling the model from a program. Ollama exposes an OpenAI-compatible API at http://localhost:11434/v1/. That phrase — "OpenAI-compatible" — is one of the most important ideas in this whole lab: it means the same code that talks to a giant cloud model can talk to your local one, just by changing the address.

  1. Write a short Python script that sends a chat message to http://localhost:11434/v1/ and prints the reply. (The official Ollama OpenAI-compatibility docs show the exact shape — use them, don't guess.)
  2. Change the prompt in your code and run it again. Now you're driving the model programmatically.
  3. Try a second, smaller model and a second, larger one. Notice the trade-off: bigger models are smarter but slower and hungrier for VRAM.

Understand what just happened

The model you ran was almost certainly quantized — shrunk down (in a format called GGUF) so it fits in your GPU's memory. That's why the same model comes in many sizes on the Hub. Ollama handled that for you; later you'll see the engine underneath it (llama.cpp) and learn to do it yourself. Prefer clicking instead of typing? LM Studio is a GUI that does the same thing. On an Apple Silicon Mac, Ollama and LM Studio work the same way (Apple's own MLX is the deeper path).

Stretch: try a reasoning model

Once the basics work, pull a reasoning model like DeepSeek-R1-Distill-Qwen-7B and watch it "think" through a problem before answering. Note in your log how its answers differ from the regular instruct model — and read its license on the model card. The huge frontier models (full DeepSeek, Kimi, GLM) are too big for one GPU; that's a later, advanced unit.

Prove it Show two things: (1) the model answering you in the terminal, and (2) your Python script getting a reply from localhost. In your notebook, explain in one paragraph what "OpenAI-compatible API" means and why it matters that your local model has one.
Module 2

Serve — like an organization would

Goal: Move from "runs on my machine" to "serves the whole class at once" — the difference between a hobby and a job.

Ollama is your on-ramp, but it isn't how a company serves a model to hundreds of users. Here you step up to a production serving engine, package it so it runs the same way anywhere, and learn the networking that turns "I ran a model" into "I stood up a service."

What you'll do

  1. Serve an instruct model with vLLM — it exposes an OpenAI-compatible server, same interface as Module 1, but built to answer many requests at once. Follow the official docs for the exact vllm serve command and model name.
  2. Call your server from a different computer on the network using the box's IP address and port — not just localhost. This is the moment "it works on my machine" becomes "it works as a service."
  3. Package the serving stack in Docker so it starts identically every time, on any machine.
  4. Lock it down: open only the port you need (firewall), and ssh into the box to run it headless — no monitor attached.

Understand what just happened

A production engine like vLLM batches many requests together and keeps the GPU busy, so it serves a whole class far better than running one chat at a time. That efficiency is the whole reason companies use engines like this instead of a desktop chat app.

On a Mac mini

vLLM is built for NVIDIA GPUs. If your box is an Apple Silicon Mac, serve with Ollama, LM Studio, or Apple's MLX instead — the OpenAI-compatible API is the same, so everything downstream still works.

Heads up

This is where it gets harder and more real. Expect to spend time reading error messages and official docs. That struggle is the skill employers pay for — most people never learn to serve a model, only to chat with one.

Prove it Show your model answering a request sent from a different computer on the lab network, and show the service running inside Docker. In your log, explain in one paragraph why a batching server serves a class better than running ollama run for each person.
Module 3

Network — turn the lab into one service

Goal: Take several boxes, each serving a model, and put them behind one address that load-balances across all of them.

This is what the lab was built for. You'll learn the pattern organizations actually run — many independent model servers behind a single gateway — and then run an honest experiment in splitting one model across machines to see why that's harder than it sounds.

The real pattern

  1. Get two or three boxes each serving a model (your Module 2 setup).
  2. Put LiteLLM in front as a gateway: one OpenAI-compatible URL that spreads requests across all your boxes, hands out API keys, and logs who used what.
  3. Test failover: send steady traffic, then pull the plug on one node. Watch the gateway route around it. That resilience is the point.

The experiment (great to learn, not to rely on)

  1. Try splitting one bigger model across two machines — with llama.cpp's RPC backend, or exo if a Mac mini is in the mix (exo is built for Apple Silicon).
  2. Measure it against a single box. You'll usually find it's slower, because the machines have to shuttle huge amounts of data over the network. That's the lesson: splitting a model wants very fast interconnect, which ordinary Ethernet isn't.
Security moment — read this

The llama.cpp RPC docs say plainly: it's a proof-of-concept, it's insecure, and you should never run it on an open network. Keep the lab on its own isolated segment. This is exactly the kind of thing a real ops engineer has to think about — treat it as part of the work, not a side note.

Prove it Show one gateway URL that keeps answering when you take a node offline. Then write up what happened when you tried splitting a model across two boxes — the numbers you measured, and why you think you saw them.
Module 4

Extend — build a tool your model can use

Goal: Build your own MCP server that gives a model a new ability, and call it from a local model.

A model that can only talk is limited. The Model Context Protocol is the open standard that lets any AI app use tools you build — think of it as a universal plug. A motivated student can get a first server working in an afternoon.

What you'll do

  1. Follow the official Build an MCP server quickstart in Python or TypeScript. Start by getting the example server running exactly as written.
  2. Add your own tool — something with a real input and output. Look something up, do a calculation, read a file, hit a simple API. Make it yours.
  3. Connect the server to a host and watch the model call your tool. Then point a local model (through the OpenAI-compatible endpoint from earlier modules) at it via an agent loop.
  4. Work the Hugging Face MCP Course for the concepts — and earn its free certificate.
Honest limitation — and it's the lesson

A small model running on one lab GPU will call your tool less reliably than a giant cloud model does. Don't be discouraged — measure it. Note when your local model uses the tool correctly and when it fumbles. That gap is a real insight into why bigger, better-tuned models follow instructions more dependably.

Prove it Show your own MCP tool being called successfully. Then log a handful of attempts driving it from a small local model — where it worked, where it didn't — and a sentence on what you think made the difference.
Module 5

Agents & RAG — reason and retrieve

Goal: Wire your model into an agent harness, then build the classic first project: chat with your own documents.

Now the model becomes the engine inside a bigger system. You'll use a real agent framework on top of your local stack, and build retrieval — the technique that lets a model answer from your documents instead of making things up.

What you'll do

  1. Use smolagents (minimal, open, local-first) or the OpenAI Agents SDK with LiteLLM to build a simple agent, pointed at your local model, that uses a tool to accomplish a task.
  2. Build a RAG pipeline: turn a folder of your own documents into embeddings (via sentence-transformers or Ollama), store them in Chroma, retrieve the closest matches to a question, and feed those to the model to answer.
  3. Ask it things only answerable from your documents. Then check it's actually retrieving — make it show which document each answer came from.
  4. Work the Hugging Face Agents Course (free certificate), and compare your local harness to a frontier one like the Claude Agent SDK.

Understand what just happened

An embedding turns text into a list of numbers so a computer can measure how similar two pieces of text are. RAG uses that to pull in the relevant parts of your documents before the model answers — which is how you get answers grounded in real sources instead of confident guesses.

Prove it Build a working "chat with my documents" that cites the source for each answer. In your log, explain what an embedding is and why retrieval makes the model's answers more trustworthy.
Module 6

Build & capstone — ship something real

Goal: Build and host a genuine application on the stack you set up, using every layer you've learned.

Everything comes together. You'll build a real app on the models the lab serves, use AI-assisted coding to move fast, and host it so other people can actually use it.

What you'll do

  1. Pick a real problem someone actually has. Design an app that touches the whole stack: a served model (Module 2), behind the gateway (Module 3), using an MCP tool you built (Module 4), inside an agent or RAG app (Module 5).
  2. Build it. Use AI coding tools — Cline or Continue (open-source, point them at your local models) or Cursor — to move fast. But read the code they generate.
  3. Host it in the lab so classmates or teachers can use it.
  4. Write it up for your portfolio, and sit whatever certifications fit your path (see the progression's cert map).
Vibe coding, honestly

"Vibe coding" — describing what you want in plain English and letting the model write it — is real and fast. It's also a trap if you never read the result. Learn the switch: vibe when you're exploring or moving fast, read every line when it matters that you understand it. For a capstone you'll show off, you want to understand it.

Prove it Ship a hosted, working app. Include a short writeup that maps each piece back to the module it came from, plus an honest reflection: where did you let AI write the code, and where did you read and understand it yourself?

That's the full arc — from your first local model to a hosted, agentic app you built on hardware you set up yourself. Very few people, at any age, can say they've done this end to end. Keep the log; it's the record of a real skill.
