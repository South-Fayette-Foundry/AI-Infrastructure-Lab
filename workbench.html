The Workbench

Before you build with the tools, you set up the shop the way professionals do — and you learn how the pieces fit into one ecosystem, not a pile of separate apps.

This is the second foundation, alongside Build in the Open (process & documentation). Together they're the "how professionals actually work" layer that sits under every technical module. The specific tools here will drift; the habit underneath won't — work in branches, review before you merge, keep your environment reproducible, and automate the boring checks. Every tool and offer below was verified against its official source in August 2026; the fast-moving ones are flagged in place.

Professionals don't just "write code." They work inside a system: an editor and a terminal on their machine, a version-control tool tracking every change, a shared platform where a team collaborates and reviews each other's work, reproducible environments so software runs the same everywhere, and automation that checks the work without anyone having to remember to. None of these is the point on its own — together they're how real software gets built without chaos. This module is about that whole picture, and about building the habits early so they're second nature by the time you're serving models and shipping a capstone.

How it all fits together

Here's the mental model to carry through everything else. Your machine is where you work; git tracks your changes locally; GitHub is the shared home where a team collaborates; and reproducibility and automation keep the whole thing sane. Read it left to right, then top to bottom.

Your machine

Editor (VS Code) + terminal + a language (Python) + an isolated environment per project.

git (local)

The version-control tool. Records every change as a save-point you can return to.

↓ push / pull ↓
GitHub (remote)

The shared home for your repo: pull requests, code review, Issues, README, releases.

Reproducibility

Environments & containers (and Codespaces) so it runs the same for everyone.

Automation (CI/CD)

GitHub Actions runs your tests and checks automatically on every change.

The one distinction people mix up

git is the tool that tracks versions of your code, running on your computer. GitHub is a website that hosts your git projects in the cloud and adds collaboration on top — reviews, issues, automation. You can use git with no GitHub at all. Most teams use both. Keep the two words straight and half the confusion disappears.

The four layers

Layer 1

The workbench

your editor, your terminal — the multiplier skills

Everything starts with being comfortable at the keyboard. A real code editor — VS Code, free, with an enormous library of extensions — and a terminal, the text interface where you drive git, install packages, and run your programs. Being fluent in the terminal is the single biggest multiplier in this whole module: it's how professionals move fast, and it's what makes every other tool here usable.

VS CodeExtensionsTerminal / shell
Learn this first

Get comfortable navigating folders, running a Python file, and reading errors in the terminal before anything else. It feels slow for a week and then it's a superpower.

Layer 2

Version control & GitHub — the core habit

the loop every engineer runs every day

This is the most important thing in the module. GitHub Flow is the standard team workflow, and it's a loop you'll run constantly:

branch→ commit→ push→ pull request→ review→ merge

You make a branch (a safe copy to work in), commit your changes as save-points with clear messages, push them to GitHub, open a pull request (PR) proposing your work, get it reviewed, then merge it in. Around that loop sit the rest of GitHub: the repository (your project's home), Issues (the to-do and bug list), the README (the front door — you already met this in Build in the Open), Releases, and fork (your own copy of someone else's project).

repobranchcommitpush / pullpull requestcode reviewmergeIssuesfork
This is where the two foundations meet

Your documentation lives inside the repo. The README, the design doc, the Architecture Decision Records from Build in the Open — they're files in your GitHub project, and your commit history becomes the automatic, time-stamped record of your process. The workbench and the documentation habit are the same habit seen from two sides.

Cert alignment: GitHub Foundations (exam GH-900, beginner-level) — and the exam fee is waived for students verified through GitHub Education. A genuinely achievable, free-for-students credential that validates exactly this layer.
Layer 3

Reproducible environments

defeating "but it works on my machine"

The oldest bug in software is "it runs for me but not for you." Professionals solve it by making the environment itself reproducible. Three levels, from simple to powerful:

  • Virtual environments — an isolated Python setup per project so one project's packages don't break another's. The built-in baseline is venv; understand that concept first.
  • uv — the modern, very fast tool (from Astral) that manages packages, environments, and even Python versions in one place. It's what a large and growing share of professionals reach for now. Learn the venv idea, then use uv as the fast way to live it.
  • Containers & dev containers — Docker packages your whole environment so it runs identically anywhere; a devcontainer.json describes a ready-to-code environment as a file. This is the professional end-state (you'll meet Docker again when you serve models in Module 2).
venvuvDockerdev containers
The zero-setup on-ramp

GitHub Codespaces gives every student an identical dev environment in the browser — no local install, no "my laptop is different" chaos. Individuals get a free monthly allowance (currently 120 core-hours + 15 GB). Consider starting the whole class in Codespaces on day one, then peeling back the layers to show what's underneath.

Layer 4

Automation — CI/CD

let the robots check the boring stuff

CI/CD stands for continuous integration / continuous delivery — the practice of automatically building, testing, and shipping your code every time it changes. Since you're already on GitHub, the natural first tool is GitHub Actions, built right in. A student's first taste is a tiny workflow that runs your tests automatically on every push — so a broken change gets caught before it's merged, not after.

CI/CDGitHub Actionsautomated tests
Second, not first

Don't rush here. Automation only makes sense once you have a repo worth testing. Introduce it after the git→GitHub loop is a habit — then a single "run my tests on every push" workflow is a satisfying, real taste of how professional teams keep quality up.

The free student toolkit

A lot of professional tooling is free for verified students — this matters for a pilot budget. Verify current offers before you build a lesson around any one of them; these change often.

  • GitHub Student Developer Pack — free for students verified through GitHub Education. Bundles GitHub Pro, cloud credits (e.g., Azure), free professional IDEs (JetBrains), and more. The single best free-tooling resource for the pilot.
  • GitHub Codespaces — free monthly allowance for individuals (120 core-hours + 15 GB), on top of anything in the Pack.
  • GitHub Copilot — a general free tier exists (currently ~2,000 completions/month), and verified students have historically had access to the full plan at no cost. What to learn first, and how it threads through the lab

Resist tool-collecting. The habit is the point; the tools serve it. Rough order of priority:

PriorityWhatWhy
1 · Learn firstThe git → GitHub loop (GitHub Flow) + terminal fluency + VS CodeThe core daily habit of every engineer; everything else scaffolds around it
2 · Learn firstIsolated environments: venv concept, then uvThe instinct that every project gets its own clean, reproducible setup

Threading it through the seven modules

Like the documentation studio, this isn't a one-and-done. It becomes how you work in every module:

  • Module 0: set up your workbench (or open a Codespace), create your first repository, and put your documentation folder inside it.
  • Module 1: commit your model-running scripts with real messages; your Decision Log is now version-controlled.
  • Module 2: do your Docker/serving work on a branch and open a pull request — even if you're reviewing your own. Pin your Python setup with uv.
  • Modules 3–5: each new piece (gateway config, your MCP server, the RAG app) is a branch → PR → merge, with the README and ADRs updated in the same repo.
  • Module 6: the capstone lives in a clean, well-structured repository with a real README, a GitHub Actions workflow running basic checks, and a commit history that is the story of how you built it.
Prove it — the workbench checkpoint Before Module 1, create a GitHub repository for your lab work, make it your first branch, add a README and your documentation-template folder, commit with a clear message, push it, and open a pull request. When you can run that loop without looking it up, you've got the habit that carries the rest of the year.
