Documentation Field Guide

Keep this with your work. A project you can defend beats one that merely runs. Capture your thinking as you go — while it's fresh and honest — so you can explain what you did, why you did it, and retrace your steps when something breaks.

The loop — four moves you travel again and again

1 · Understand the need→2 · Decompose the problem→3 · Build & iterate→4 · Document throughout↺

The five things you keep

1 · Decision Log — every work session. Dated running notes: goal, what you tried, what happened, what you decided, why.
2 · README — write it early. The front door: what it does, who for, how to run it, how it works.
3 · Design Doc — before anything big. Goals, non-goals, your design, and the alternatives you considered.
4 · ADRs (Architecture Decision Records) — per real decision. One small note per meaningful, hard-to-reverse choice.
5 · Retrospective — at the end / when it breaks. What went well, what went wrong (causes, not blame), what you'd do differently.
Bonus: your git commit history with clear messages is documentation too — an automatic, time-stamped trail.

Templates — copy these

# Decision Log entry
Date: ____   Module: ____
Goal: what I set out to do
Tried: what I actually did
Happened: result / the error
Decided: what I changed
Why: the reason
Next: open question / next step
# ADR-00_: short title
Status: proposed | accepted | superseded
Context: the problem & constraints
Decision: what we chose
Consequences: what gets easier,
   what gets harder (the trade-off)
# README skeleton
## Project  one line: what & who for
## Problem  why it exists
## Run it  steps someone could follow
## How it works  3-5 sentences
## Decisions  links to your ADRs
## Limits  what it can't do yet
## Credits  incl. each model's license
# Retrospective
Set out to: ____
What happened: ____
Went well: ____
Went wrong: causes, not blame
Root causes: ____
Do differently: ____
Action items: each with an owner
Capture as you go, and it adds up. M0: start the log. M1: ADR for your model choice. M2: README + real commits. M3–M5: an ADR per big decision, keep the README current. M6: full design doc up front, then a retrospective at the end. By the capstone your portfolio has assembled itself — and that portfolio is your strongest credential.
